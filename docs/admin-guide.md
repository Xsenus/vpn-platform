# Руководство администратора

Документ закрывает roadmap-пункт `P10-DOC-002` и описывает фактические разделы админки VPN Platform. Админка доступна локально по адресу `http://127.0.0.1:5175`, на VPS обычно публикуется как `/admin/`. Для входа нужен пользователь с ролью администратора.

Доступ к административным API защищен RBAC: пользователь должен иметь административную роль, а все чувствительные операции должны проходить через авторизованный admin token.

Локальный режим без Docker:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\start-local.ps1
```

Локальный администратор по умолчанию: `admin@local.test` / `LocalAdminPassword123!`. Если аккаунт потерян или пароль нужно сбросить:

```powershell
$env:ASPNETCORE_ENVIRONMENT="Local"
$env:AdminBootstrap__Enabled="true"
$env:AdminBootstrap__Email="admin@local.test"
$env:AdminBootstrap__Password="LocalAdminPassword123!"
dotnet run --project backend\src\VpnPlatform.Api\VpnPlatform.Api.csproj -- admin-bootstrap
```

## Дашборд

Дашборд - первый экран оператора. Он показывает продажи, состояние тарифов, платежных провайдеров, VPN-инфраструктуры, очередей и фоновых задач.

Что проверять перед включением продаж:

- есть хотя бы один активный платный тариф;
- есть готовый web-провайдер оплаты в нужном режиме;
- webhook URL заполнен для production-провайдера;
- есть активный VPN-сервер или 3x-ui панель с inbound-ами;
- health/readiness не показывают критические блокеры;
- кнопки быстрых переходов ведут в проблемный раздел.

Если дашборд показывает critical-пункт, сначала исправьте его в указанной вкладке, затем обновите данные.

## Пользователи

Раздел нужен для операционной поддержки клиента. В карточке пользователя проверяются профиль, роли, подписки, платежи, VPN-доступы, обращения и реферальные начисления.

Типовой порядок работы:

1. Найдите пользователя по email, Telegram или идентификатору.
2. Проверьте активную подписку и последний заказ.
3. Если у клиента не работает VPN, перейдите к связанному VPN-доступу и выполните синхронизацию.
4. Если проблема платежная, откройте связанный платеж в разделе "Оплаты".
5. Все ручные действия должны оставлять запись в аудите.

## Оплаты

Раздел "Оплаты" объединяет платежные аккаунты, платежи, webhook-события и возвраты. В публичный сайт и кабинет должны попадать только включенные и готовые web-способы оплаты.

Поддерживаемые провайдеры:

- YooKassa: Shop ID, API secret, webhook URL, IP allow-list для production.
- RoboKassa: merchant login, password/signature secret, Result URL.
- YooMoney: receiver wallet, notification secret, quickpay/webhook settings.
- CloudPayments: Public ID, API password, HMAC secret, `hostedCheckoutUrl`.
- TBank Acquiring: TerminalKey, Password, notification URL.
- Prodamus: payform URL, signature secret.
- Stripe: secret key, webhook endpoint secret.
- PayPal: client id, client secret, webhook id.
- Telegram Stars: отдельный bot-only flow; web checkout должен оставаться fail-closed до полноценного Telegram invoice flow.

Правила настройки:

1. Выберите провайдера, режим `Sandbox` или `Production` и публичное название.
2. Заполните обязательные поля именно для выбранного провайдера.
3. Секреты вводятся как write-only: API не должен возвращать исходные значения после сохранения.
4. Укажите webhook URL и webhook secret, если провайдер требует подпись уведомлений.
5. Нажмите "Проверить подключение".
6. Включайте аккаунт только после успешной проверки готовности.

Для локальной проверки используйте sandbox-аккаунты: checkout создается без реальных денег и без внешних API. Для live-провайдеров нужен отдельный smoke по кабинету каждого провайдера; sandbox-header нельзя принимать в production.

## Тарифы

Тариф управляет тем, что пользователь покупает на сайте и в кабинете: название, цена, валюта, срок действия, описание, преимущества, публикация и сценарий выдачи.

Минимальная проверка перед публикацией:

- цена больше нуля для платного тарифа;
- валюта соответствует подключенным провайдерам;
- срок действия указан в днях;
- описание и преимущества понятны пользователю;
- выбран сценарий выдачи или оставлен `auto`;
- тариф активен и виден на витрине.

Изменение цены влияет только на новые заказы. Уже созданные платежи и подписки должны сохранять зафиксированную сумму заказа.

## Подписки

Раздел показывает активные, истекающие, отмененные и заблокированные подписки. Администратор может продлить подписку вручную, заблокировать, разблокировать или отменить ее.

Ручные операции используйте только с понятной причиной: например `manual_admin_extend`, `manual_admin_action` или ссылка на обращение поддержки. Это важно для аудита и последующего разбора инцидентов.

## VPN-доступы

Здесь отображаются выданные ключи пользователя: провайдер, статус, сервер, подписка, дата окончания, URI, QR-код и история событий.

Основные действия:

- скопировать URI или показать QR-код;
- отключить доступ, если подписка спорная или пользователь нарушает правила;
- включить доступ после разблокировки;
- синхронизировать доступ с провайдером;
- сбросить счетчик трафика, если это поддерживает провайдер.

Публичные ссылки доступа не должны попадать в логи, ошибки или раздел "Что нового".

## Серверы

Раздел "Серверы" описывает VPS-ноды, на которые можно выдавать VPN-доступы или готовить инфраструктуру. В карточке сервера важны host, SSH-порт, пользователь, provider, регион, capacity, приоритет, режимы `acceptNewUsers` и `isEnabled`.

Перед использованием сервера:

1. Заполните host и SSH-параметры.
2. Укажите owner/source tags, если сервер относится к отдельному клиенту или окружению.
3. Запустите health-check или precheck.
4. Убедитесь, что сервер не в `Maintenance` и не архивирован.
5. Не включайте прием новых пользователей, пока нет рабочего VPN-провайдера или 3x-ui inbound.

Секреты SSH и панели должны храниться через защищенное хранилище и не отображаться после сохранения.

## 3x-ui панели

Раздел "3x-ui панели" нужен для подключения реальных x-ui/3x-ui панелей, inbound-ов и клиентов. Поддерживаемые протоколы выдачи: VLESS, VMess и Trojan.

Порядок подключения:

1. Добавьте панель: base URL, логин, пароль, SSL-настройки и связь с сервером.
2. Нажмите проверку подключения.
3. Синхронизируйте inbound-ы.
4. Проверьте, что inbound активен, имеет лимиты и корректный протокол.
5. Создайте тестового клиента через sandbox/live smoke.
6. Проверьте, что URI открывается в клиенте VPN и QR-код соответствует URI.

Если панель недоступна, выдача должна завершаться fail-closed: заказ не должен считаться успешно выданным без реального доступа.

## Поддержка

Раздел используется для обращений пользователей из кабинета и Telegram. Оператор видит тему, статус, сообщения, внутренние заметки и связанного пользователя.

Рекомендации:

- не храните секреты, пароли и приватные ключи в тексте обращения;
- фиксируйте ручные действия ссылкой на обращение;
- закрывайте обращение только после проверки результата пользователем или после понятного ответа.

## Аудит

Аудит фиксирует административные действия, платежные переходы, webhook-обработку, выдачу VPN-доступов, ротацию секретов и provisioning-события.

Проверяйте аудит после:

- изменения платежного провайдера;
- ручного возврата;
- продления или блокировки подписки;
- отключения VPN-доступа;
- ротации секретов;
- live provisioning/deploy.

## Telegram-бот

Раздел управляет Telegram-ботом: режим LongPolling или Webhook, bot token, secret token, admin chat id и проверка подключения.

Порядок настройки:

1. Создайте бота через BotFather и получите token.
2. Введите token в write-only поле.
3. Выберите режим работы.
4. Для webhook укажите публичный URL и secret token.
5. Укажите admin chat id для служебных уведомлений.
6. Нажмите "Проверить подключение".

Telegram Stars не должен отображаться как обычный web-провайдер до полноценного invoice flow. Для продаж через бота проверяйте отдельный Telegram-сценарий покупки.

## Что нового

Раздел "Что нового" управляет заметками релизов, которые видит пользователь после входа в кабинет. Каждая запись должна иметь `releaseId`, версию, дату публикации, заголовок, краткое описание, активность, источник и список пунктов.

Правила публикации:

- пишите текст для пользователя, а не внутренний changelog;
- не публикуйте секреты, host-ключи, токены и приватные IP, если они не предназначены пользователю;
- будущая дата публикации скрывает запись до наступления времени;
- после крупной задачи добавляйте release entry и тестовое покрытие через `ReleaseDocumentationGuardTests`.

## FAQ

FAQ управляет вопросами на главной странице и публичной странице FAQ. Для каждой записи задаются категория, вопрос, ответ, сортировка, активность и видимость.

Перед публикацией проверьте:

- вопрос сформулирован так, как его задает пользователь;
- ответ не обещает неподключенные live-провайдеры или неподтвержденную VPN-выдачу;
- неактивные записи скрыты от публичного сайта;
- сортировка не ломает порядок популярных вопросов.

## Контент сайта

Раздел управляет текстами главной страницы: hero, SEO, преимущества, отзывы, CTA и другие блоки. Изменения должны быть короткими, понятными и едиными по стилю с публичным сайтом, кабинетом и админкой.

После изменения контента проверьте публичный сайт:

```powershell
npm run build --prefix frontend
npm run e2e:public --prefix frontend
```

## Сценарии

Сценарии описывают, что происходит после оплаты, при ошибке, возврате, продлении и окончании подписки. Тариф может выбрать основной сценарий по ключу, а сценарий может быть разрешен только для конкретных тарифов.

Типовые сценарии:

- sandbox-выдача для локальной проверки;
- автоматическая выдача через 3x-ui;
- ручная проверка перед выдачей;
- fail-closed при недоступности VPN-провайдера;
- продление существующего доступа;
- отключение после возврата или окончания подписки.

## Подготовка VPS

Раздел "Подготовка VPS" управляет precheck, provisioning run, deploy, rollback и отменой запусков. Он нужен для безопасной подготовки серверов без прямого ручного вмешательства.

Безопасный порядок:

1. Запустите precheck и изучите report.
2. Убедитесь, что режим `dry-run` или `validation-deploy` соответствует окружению.
3. Для live deploy должны быть явно включены operator gates: `Provisioning__LiveExecutionEnabled=true`, `Provisioning__AllowLiveDeploy=true` и tags `explicit-live-provisioning:true`.
4. Не запускайте live deploy, если система показывает `live-deploy-blocked`.
5. После deploy проверьте health, 3x-ui, inbound и тестовый доступ.
6. Для отката используйте rollback-сценарий и фиксируйте причину.

## Быстрый приемочный чеклист

- Админ входит без ошибок и видит вкладки: Дашборд, Пользователи, Оплаты, Тарифы, Подписки, VPN-доступы, Серверы, 3x-ui панели, Поддержка, Аудит, Telegram-бот, Что нового, FAQ, Контент сайта, Сценарии, Подготовка VPS.
- Платежные провайдеры имеют provider-specific поля и кнопку "Проверить подключение".
- Публичный сайт показывает только готовые web-способы оплаты.
- Telegram Stars не смешивается с web checkout.
- Тариф можно связать со сценарием.
- VPN-доступ можно синхронизировать, отключить и показать как QR.
- 3x-ui panel/inbound/client flow проверяется отдельно от sandbox.
- Все ручные операции пишутся в аудит.
- Секреты остаются write-only.
- После изменений проходят backend/frontend проверки и local SQLite smoke.
